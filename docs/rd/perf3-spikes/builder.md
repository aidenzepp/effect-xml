# Spike perf3-sp-builder: a plan-driven builder plus one structural Schema decode

Unit `perf3-sp-builder`, phase 3 brief Step 1 items 1, 2 and 4. This is an R&D spike. The prototype lives in `work/spikes/perf3-builder/` (gitignored); this file is the durable record.

## Result

The prototype cuts the Schema layer of a `bank-4m` typed decode from about 70 ms to about 11 to 14 ms, 5 to 6.5 times faster, on Bun and on Node. The JIT is not required: interpreted, the layer is still about 14 ms. Its decoded values deep-equal the current implementation's on every input tried. Build it, with the error policy in the recommendation.

| bank-4m Schema layer, median ms (same resolved root as input)           | Bun  | Node |
| ----------------------------------------------------------------------- | ---- | ---- |
| Current `Schema.decodeUnknownSync(ItemBank)(root)`, JIT off             | 71.3 | 69.2 |
| Current, `SchemaJITCompiler.enable(ast)` on `ItemBank` and `fromString` | 63.3 | 56.6 |
| Current, JIT enabled process-wide                                       | 57.6 | 55.9 |
| Prototype builder + structural decode, JIT off (the no-eval mode)       | 13.3 | 14.2 |
| Prototype, `SchemaJITCompiler.enable(structural.ast)`                   | 11.8 | 10.5 |
| Prototype, JIT enabled process-wide                                     | 10.8 | 10.0 |

With the Schema layer this small, the XML layers dominate: tokenizer, resolver and collector (`decodeTree`) take 34 to 39 ms on Bun and about 49 ms on Node, about three quarters of the prototype's end-to-end time.

## What was built

1. **Builder** (`structural.ts`, `nodeOf`, `build`, `buildRoot`). Per Plan, once, it compiles a node: attribute Clark name to struct key, a `data-*` flag, slots by Clark name with their index and cardinality, mixed members by Clark name with their wire tag, and the open flag. Child nodes are built lazily, so `suspend` recursion works. The walk is plain JavaScript over a `ResolvedElement` record, with no Schema and no Effect. It checks what `decodeElement` checks today: undeclared attribute, non-blank text in `empty` or `elements` content, an element in `text` content, an undeclared child of closed content, a second child for a `one` or `optional` slot, and the root's Clark name. It emits raw strings, reshaped:
   - attributes under their struct keys, and `data-*` attributes under their own names;
   - `$text` as the joined string children;
   - `elements` slots as a child object, an array for `many`, omitted when an `optional` slot is absent; open content adds `"*"` holding the raw `ResolvedElement`s;
   - `mixed` content as `$children` items: `{ _tag: "$text", text }`, `{ _tag: <wire>, value: <child object> }`, or `{ _tag: "*", element }` for open content.
2. **Structural codec** (`structuralOf`). One `Schema.Struct` per Plan, cached by Plan. Attribute and `text` fields reuse `Schema.toCodecStringTree(leaf)`, exactly as `compile` does. `elements` slots nest the child's Struct, wrapped in `Schema.Array` or `Schema.optionalKey`. Open slots are `Schema.Array(ResolvedElementSchema)`. `mixed` is `Schema.Array(Schema.Union([...]))` of Structs discriminated by a `_tag` literal. `data-*` uses `Schema.StructWithRest` with the same `TemplateLiteral` record as `compile`. Recursion goes through `Schema.suspend`. One `Schema.decodeUnknownSync(structural)` call decodes the whole document.
3. **API.** Unchanged. The prototype only reads Plans through `planOf`; `XmlSchema.Element(...)` and its per-element codecs are untouched. In a real slice the builder and the structural codec would sit inside `decodeString` and the record channels, behind the same entry points.

The corpus covers recursion through `suspend` (`div`, `mrow`), mixed content, `data-*` attributes, a branded leaf (`Identifier`), and optional and repeated slots. The bank covers `Schema.Finite` and `Schema.Boolean` leaf transformations.

**Errors.** Failures split by layer:

- **Schema-layer failures** (a leaf rejects its string, a required attribute or child is missing): 77 of 77 translate through the existing `toDecodeError(plan, root, error)` to the same XML path, the same reason, and the same message as today, positions aside. The structural codec uses the same struct keys, `$children` indexes, and `value` key as the current target Structs, so the translator in `issue.ts` needs no change.
- **Builder-layer failures** (307 cases): the spike's messages are placeholders. Two things must hold before this ships:
  1. The messages must be the current ones; they live in `compile.ts` and can move to the builder unchanged.
  2. **Ordering differs.** The builder checks the whole tree before Schema decodes any leaf. Today each element runs its own structural checks and then its fields in declaration order. A leaf failure in an early slot plus a structural failure in a later slot is therefore reported differently. Example: `conformance-adaptive-absent.xml` reports today a missing `qti-item-body`; the builder trips first on the non-empty `qti-response-processing`. Under `errors: "all"` the issue sets differ too.

## Recommendation

1. **Builder shape: build it.** A plain-JS walk over `ResolvedElement` records, compiled per Plan. Input stays the collector's records, so documents and streams share it. Fusing the builder into the collector, to skip the `ResolvedElement` tree, is a later option if the XML layers are attacked (Step 2); it would also save part of the collector's cost.
2. **Codec shape: build it.** One structural Struct/Array/Union codec per root, derived from Plans, with leaf codecs reused through `toCodecStringTree`. Wrapped element codecs become leaf fields that run the user's codec on the raw `ResolvedElement`.
3. **Error policy: fast path for success, current path for failure.** When the builder or the structural decode fails, rerun the current per-element decode on the same root and report its error. Errors, paths, positions and `errors: "all"` stay identical by construction, and the per-element codecs must stay anyway, because `XmlSchema.Element` still returns a composable `Schema.Codec` (R1, R2). Cost on `bank-4m-bad-last`, Schema layer: 92 ms on Bun (current 77 ms) and 79 ms on Node (current 65 ms), a failure fast attempt of about 14 ms paid only on failure. The alternative, matching today's error order inside the builder by leaving poison values for the structural decode to report, is possible but needs its own differential proof; prefer the fallback unless failure latency matters.
4. **JIT policy evidence.** Per-AST `SchemaJITCompiler.enable(structural.ast)` gets most of the process-wide gain: on Bun 11.8 ms against 10.8 ms, on Node 10.5 ms against 10.0 ms. It has no global side effect, which supports per-AST enable on the library's own structural ASTs. The no-eval fallback, JIT off, is still about 5 times faster than today. The final policy belongs to item 6 of the brief.

## Method

- Machine: Apple M4 Pro, 14 cores, 48 GB. The machine was heavily shared: other seats ran benchmarks concurrently, and the 1-minute load average was 12 to 35 during the matrix (median 25). Variance is visible in some rounds; the ratios held in every round.
- Runtimes: Bun 1.4.2 and Node v26.13.0 (native type stripping). `effect` 4.1.2. Source: main at `a7a93d5` plus foreign uncommitted edits under `bench/` (`case-process.ts`, `run.ts`, `types.ts`, `harness/jit*`) that the prototype does not import.
- Input: `bank-4m` (4,194,472 bytes, one document) from `bench/inputs/synthetic.ts`, decoded as `ItemBank` with `maxElementNodes` and `maxElementSize` set to `Infinity`.
- Harness: `work/spikes/perf3-builder/bench.ts <mode>`, one process per mode (the process-wide JIT cannot be turned off again). 5 warm-up iterations, then 21 timed iterations with `performance.now()`, median per run. The matrix ran 3 interleaved rounds (each round runs all modes on Bun, then on Node); the tables give the median of the three run medians. Raw output: `work/spikes/perf3-builder/runs.txt`.
- Phases:
  - Current Schema layer: `Schema.decodeUnknownSync(ItemBank)` on a resolved root decoded once beforehand.
  - Prototype: `buildRoot` on a fresh `decodeTree` root, then `Schema.decodeUnknownSync(structural)` on the result. Each is timed on its own, and their sum is reported.
  - Both read the same root, so this comparison is like for like.
- End to end, for context (median ms, Bun / Node, JIT off): current `fromString` 129.1 / 128.7; prototype `decodeTree` plus builder plus structural decode 47.5 / 63.6. The prototype total skips the `fromString` Schema wrapper, the `xml.decodeString` span and its debug log, so these two totals are not like for like; the Schema-layer table is.
- Failure path: `work/spikes/perf3-builder/fail-path.ts`, `bank-4m-bad-last`, 5 warm-ups and 21 iterations, JIT off.

## Not measured

- **Encode.** Out of this unit; see `encode.md`.
- **AOT and strict-CSP environments.** Only the JIT-off interpreter, which is what a no-eval environment falls back to, was measured. `SchemaAOTCompiler` was not tried (brief item 7, another unit).
- **Which nodes the JIT compiles** around user transformations and checks (brief item 8). The gain on `ItemBank` and the equality on the branded corpus show it compiles around them correctly here, but which subtrees fell back to the interpreter was not isolated.
- **The other metrics of the want's amendment**: latency percentiles beyond p25/p75, CPU, RSS, heap, allocation rate, GC, time to first record, and scaling. Wall time on `bank-4m` only; the phase slices own the full metric set.
- **Streaming records** through `decodeSchema` and `decodeSchemaString`, and other bank sizes for timing. Equivalence covered bank-16k, bank-256k and bank-4m, but only `bank-4m` was timed.
- **computis on this run.** Its ~21 ms figure comes from `docs/rd/performance.md` and was not re-measured under this load.
- **Builder-layer error messages and order**: placeholders in the spike; see Errors.
- **Wrapped element codecs** in the structural codec: refused by the spike; see Coverage map.
- **Property-based fuzzing**: the mutation differential is seeded and regex-based, not generated from schemas.

## Open questions

- Is the failure-path cost of the fallback (about 1.2 times today's Schema layer) acceptable, or does the owner want exact error order natively in the builder?
- Should a wrapped element codec be rebuilt over the structural node by AST surgery for speed, or run as an opaque leaf at today's speed?
- With the Schema layer at about 11 to 14 ms, the XML layers (34 to 50 ms) now set the end-to-end time. This is the input to the Step 2 tokenizer decision rule.

## Tensions T1-T5

### T1. Layering mechanism: IR compiler or AST rewrite

**Ruling: (a).** The DSL object form lowers to a closed IR and one `Element <-> value` compiler interprets it. There is no AST rewrite in the library, not as core and not as escape hatch. D6 is therefore **reversed** to branch C (closed IR), not amended.

What "one definition, both directions" requires of the mechanism, and where the spike already meets it:

1. One producer of truth per element: the DSL object is lowered once to a `Plan` (`spikes/declaration-dsl/element-codec.ts:62-70`; lowering at `xml-dsl.ts:132` and, for the annotation surface, `xml-annotations.ts:69`). The `Plan` is the branch's `ElementSpec { name, attributes, contentMode, children }` by another name.
2. Both getters are generated from that `Plan`, never written by the consumer: `decodeElement` (`element-codec.ts:138-231`) and `encodeElement` (`:233-291`).
3. Exactly one `Schema.decodeTo` per element, from `ElementSchema` (a `Schema.declare` over the upstream `Xml.Element`, `:38`) into a target `Schema.Struct` derived from the same `Plan` (`compile`, `:296-338`). Attribute and text leaves are `Schema.toCodecStringTree(consumerSchema)` (`:299`, `:306`); child slots are the child element codecs themselves (`:308-316`), so Schema's own nesting decodes each child once by its own definition and the consumer's `Type` is inferred from the target struct.
4. `data-*` is `Schema.StructWithRest` plus a `Schema.Record` keyed by `Schema.TemplateLiteral(["data-", Schema.String])` (`:326-330`); mixed content is `Schema.Array(Schema.Union([TextItem, ...members]))` with a tagging `decodeTo` per member (`:109-131`).

Evidence that this clears the gates: SPIKE-05 C1 = 5 and C2 = 5 for both surfaces on the benchmark subset, `data-*` included, with the same `AssessmentItem` value used for `Schema.decodeUnknownEffect` and `Schema.encodeEffect` (RESULT "round trip through one definition", 4 tests; re-run here, 19/19).

Why not (b), the AST rewrite SPIKE-06 favoured: the public-constructor rewrite (`spikes/schema-layering/approach-b.ts:174-252`) reports as unsupported every composite with an encoding chain (`:187-191`), every `Objects` with index signatures (`:194`, which is `data-*`, a C2 gate item), and `Declaration`/`Any`/`Unknown`/`ObjectKeyword` (`:240-245`, which is every `Schema.Class`). Reaching them needs `applyToSelfOrLastLinkEncoding`, `replaceEncoding`, `Objects.recur`, `getIndexSignatureKeys`, all `@internal` and absent from `dist/*.d.ts` (SPIKE-06 stability table). SPIKE-06 C2 = 3 for B. The rewrite's one advantage, "a plain annotated `Schema.Struct` is a valid definition without a second producer", is already delivered on the IR path by the 119-line annotation walker of SPIKE-05 A (`xml-annotations.ts:69-134`), which lowers an annotated Struct to the same `Plan`. So the rewrite buys nothing the IR lacks and costs a second mechanism plus an `@internal` dependency.

Why not (c), IR primary with rewrite for leaves: leaves are already `toCodecStringTree`, which is public and stable (`Schema.ts:18441`), and both spikes used it unchanged. There is no leaf the rewrite reaches that the IR compiler does not.

On SPIKE-06 A scoring C1 = 0: that approach hand-wrote the getters (`elementToTree` 25 lines, `treeToElement` 55 lines) and SPIKE-06 itself concluded "the only way to generate them is an IR, which is C". SPIKE-05 generated them. A-as-implemented in SPIKE-06 and (a) here are not the same thing; the gate failure does not transfer.

Encode to text: the compiler's encode yields an `Xml.Element`; SPIKE-03's `elementEvents` (13 lines, `spikes/round-trip/pipeline.ts`) walks it to events for `Xml.encode`. Streaming encode is per record, which is the only streaming granularity this library offers (D4).

- Not verified: the compiler against `Schema.Class` bodies (SPIKE-05 "not implemented"); order validation across different child names inside `elements` mode (XSD sequences are ordered; the compiler groups by name, `element-codec.ts:189-223`); `optionalKey` attribute behaviour under `withDecodingDefault` chains.
- Producer fact that changes it: upstream exports the four Config helpers as stable public API, or adds a custom AST node kind (`SchemaAST.ts:54-75` is closed today). Even then the ruling would only reopen, not flip, because the IR path already passes both gates.
- Risk: P1 if the first milestone re-introduces a rewrite "for Class users"; P2 for the `elements`-mode order gap (recorded, R3).

### T2. Error paths and where positions attach

**Ruling: the translation pass is accepted, driven by the `Plan`, run at the decode entry point with the input element in hand.** Issue paths are struct-keyed in every mechanism (SPIKE-06 "Issue paths": `Pointer` segments are the struct's property keys in A and B alike; SPIKE-05 evidence 6 shows the same for both surfaces). The branch claim that a rewrite yields input-shaped paths is false and is a corpus correction below.

Shape of the pass: SPIKE-06's `translateIssue` (`approach-b.ts:336-383`, 50 lines) walks `Pointer`/`Composite`/`Encoding` and re-points segments through per-key metadata. In the library the metadata is the `Plan` tree instead of AST annotations: attribute keys become `@name`, `elements`-mode slot keys become the child wire name, `mixed`-mode positional indices become `name[k]` by looking at the input element's children (the translator therefore takes the input `Element`, which the decode entry point holds; the `Issue` alone does not carry it unless `reportInput: true`). Printed form is XPath-like with one-based same-named-sibling indices (`/qti-assessment-item/qti-item-body/p[2]/@data-foo`), which settles SPIKE-07 open question 1 in favour of what XML tools print; the locate scanner's zero-based internal convention is an implementation detail covered by its agreement test.

Positions: `SchemaIssue` has no slot for them (`SchemaIssue.ts:156-163`, substrate map 2.3), so the public decode failure is a library error that pairs the translated issue with the XML path and an optional `{ line, column }`; upstream `XmlError` stays the cause for well-formedness failures (effect-design ruling already in `error-reporting.md`). The lookup attaches in two places and nowhere else:

| Entry point                                                   | Text retained? | Position source                              | Default                |
| ------------------------------------------------------------- | -------------- | -------------------------------------------- | ---------------------- |
| Decode from a string (tree mode or `elements` over a string)  | yes            | post-hoc locate (SPIKE-07 C) on failure only | on                     |
| Decode from a byte or chunk stream (`Xml.decode`, per-record) | no             | opt-in position channel (SPIKE-07 B)         | off, `positions: true` |

Per-record streaming with positions means the resolver channel (T4) forwards the position the B channel attached to each `StartElement`; without `positions: true` the path is reported and the position is absent, honestly.

Which failure surface the library exposes (SPIKE-06 open question 2): the Effect-native one. `Schema.decodeEffect` fails with `Schema.SchemaError`; the library's typed error wraps that issue after translation. Raw `SchemaIssue` stays reachable through `SchemaParser` for callers who want it; the library does not add a third formatter.

- Not verified: translation of `AnyOf` issues from mixed-content unions (SPIKE-06 translated `Pointer`/`Composite`/`Encoding` only); locate on attribute positions inside a start tag (both spikes report the tag start only).
- Producer fact: upstream adds a position or annotation slot to `SchemaIssue`, or positions to `StartElement` events (then B's structural cost disappears and the table collapses to one row).
- Risk: P2. Paths are correct in every spike; positions are an additive quality, and the one-based convention is a documentation fact.

### T3. Mixed content: name dispatch now or recorded risk

**Ruling: requirement of the first milestone, by the pragmatic mechanism, not a custom dispatcher.** SPIKE-05 open question 2 records that `Schema.Union` over element codecs tries every member and reports every miss, so one bad attribute inside `<p>` yields four issues. That fails C10 ("names the XML path and the expectation"), weight 10, on the most common consumer path. The fix is to give Schema's own union indexing something to index on: SPIKE-01 evidence 4 verified that when each member's Encoded side carries `name: Schema.Literal(name)`, `Schema.Union` selects the member by that sentinel on decode (`SchemaAST.ts:3540-3600`) and by `_tag` on encode, with 17/17 tests. So `ElementSchema` moves from `Schema.declare(isElement)` (`element-codec.ts:38`) to a per-element `Schema.Struct({ name: Schema.Literal(plan.name), attributes, children })`. No new code path, one existing Schema feature used as designed.

SPIKE-01 C3 = 4 (16 formatted lines, 8 statements) is accepted; the criterion's line-versus-statement ambiguity is a corpus correction, not a product gap.

Whitespace-only text runs in `mixed` content are kept verbatim (XML semantics; SPIKE-01 open question 5 and SPIKE-05 "not implemented"); `elements` mode drops them (`element-codec.ts:193-198`). A renderer trims. No policy option in the first milestone.

- Not verified: the member order of issues once indexed. Source-verified at the strategic review (`strategic-review.md` C1): the index survives the tagging `decodeTo` (`toCandidate` walks the encoding links to their last target, `SchemaAST.ts:3389-3402`), and it does not fire for a `Schema.suspend` member (`:3391` returns `unknown`), which is a runtime-type fallback tried on every child; the issue translator selects by element name for that reason.
- Producer fact: a measured case where sentinel indexing does not fire (then a Plan-driven member selector, about 20 lines, is the fallback and still not a framework).
- Risk: P1 if shipped without it (consumer-visible wrong-looking errors on every mixed-content failure); P2 after.

### T4. Namespace resolver: cost versus gate, and where it runs

**Ruling: D2 holds; the gate overrides the cost condition; the resolver is a library-level Channel over `Xml.Event`, and the per-record collector that consumes it is in-house.**

Gate over cost: `criteria.md` states that a 0 on a gate disqualifies regardless of total, and D2's reversal condition was a conjunction ("resolver dominates ... and the corpus never varies prefixes"). The first half is met (233 lines, SPIKE-02 C9 = 3) and the second is false on a real fixture: `bpig-mathml.xml` re-binds the default namespace on an inner `<math>` with no prefix change, so prefix-as-written yields equal trees for two documents in different vocabularies (SPIKE-02 C4 = 0 for B, test at `namespaces.test.ts:227`). Expanded names at decode, schema prefix map for authoring and encode (SPIKE-02 A plus C), unprefixed attributes in no namespace.

Where it runs: over events, between `Xml.decode` and collection, as a `Channel.fromTransform` following the upstream `makeChannel` pattern (`Xml.ts:568-616`). Three facts decide it against a post-hoc pass on the `Element` tree:

1. Records from `Xml.elements` carry no ancestor `xmlns` or `xml:lang` (SPIKE-04 ancestor-scope test; `Collector` stores `event.attributes` as-is, `Xml.ts:1742-1757`), and a `Stream.tap` can recover root scope but not an exact per-record scope when declarations change inside a chunk (SPIKE-04 caveat).
2. The event boundary is where positions attach (T2) and where SPIKE-02 already built it (`resolver.ts:130-178`, a `Stream.runFoldEffect` over `Xml.decodeString` events with a scope stack).
3. Resolved events are the library's own type (expanded names, `xmlns*` consumed, in-scope prefix map carried on each start element for `xsi:type`), so the collector that groups them into per-record trees is ours: about 30 lines (SPIKE-02 "tree assembly inside `step`"), the same shape as upstream `Collector`, matching the record path by expanded name. This is also where the T5 budget is enforced, so the in-house collector is not a parallel implementation for its own sake.

`Xml.elements` remains available to consumers who want raw unresolved trees; the library core does not route through it.

Attribute keys on the resolved element: Clark strings (`{uri}local`, or `local` for no namespace) as `Record` keys (SPIKE-02 open question 1). A `Record` is the Schema-native shape `StructWithRest` reads; a value-equality `HashMap` would add a type Schema cannot decode without another layer. Definitions author with prefixes through the prefix map (`qname(map)("m:math")`, `resolver.ts:182`).

`xsi:type`: deferred (want). The resolved element carries its in-scope map, so a QName-valued attribute codec is additive later; QTI's `qti-*-interaction` family does not need it (README open question 3).

- Not verified: resolver throughput on the 55 MB synthetic (SPIKE-02 ran kilobyte fixtures); encode-side `xmlns=""` undeclaration and per-subtree declaration placement (SPIKE-02 "not implemented"); that the in-house collector matches `Xml.elements` chunk-emission semantics exactly.
- Producer fact: upstream `Xml.elements` grows a hook that hands ancestor attributes or a name-rewrite callback to the collector (then the collector returns upstream and only the event resolver stays).
- Risk: P2. Resolver correctness is gate-tested on real fixtures; the cost is bounded and justified piece by piece in SPIKE-02.

### Ruling: text streams are never encoding-checked (phase-3 lock 3 over lock 2)

Implemented at `2fe1c9b`. `phase-3.md` lock 3 (text streams are never encoding-checked, as `decodeString`) wins over lock 2's `TextEncoder` route. Under `positions: false`, a text stream is parsed by `Xml.decodeString` and a byte stream by `Xml.decode`, so a declared non-UTF-8 encoding fails only on bytes. Under `positions: true`, the byte-mode parity rules of lock 3 are unchanged.

### T5. Limits: shape of the library budget

**Ruling: per collected record, a node-count budget beside the inherited character count. Not per document.**

Evidence: upstream `maxElementSize` counts UTF-16 code units of names, attribute names and values, and text (`Xml.ts:272-274`, `grow` at `:1783-1788`). Two documents with the same counted size 1,000,001 retain 122 MB and 1 MB after GC (SPIKE-04 "limits" test), 128 versus 1 bytes per counted character; the branch set "more than an order of magnitude" as the reopen condition and 122x clears it. What the character count misses is per-node overhead, so the honest second limit counts nodes (element starts plus text runs) in one collected record. Per record because the collector (T4) materialises one record at a time and SPIKE-04 shows memory bounded by the largest record (C' live heap flat at 1.8 MB over 160,080 records); in tree mode the record is the whole document, so a per-record budget covers the single-document case by construction. A per-document cap is the stream's concern (bytes read), and `maxTokenSize`/`maxDepth` stay inherited at the parser.

Proposed surface: `maxElementSize` (inherited semantics, same default 16 MiB) and `maxElementNodes` (default 1,000,000, which SPIKE-04 measured at about 128 MB worst case for empty elements). Both enforced in the in-house collector, both failing with a `Limit`-kind library error that names the record's root element, as upstream does. The error kind name and the default number are the Planner's to confirm against the error-messages skill; the shape is settled.

- Not verified: per-node retained size on runtimes other than Bun 1.4.2 on Apple Silicon; whether events retaining their input chunk (`Xml.ts:317-320`, SPIKE-04 open question 4) inflates the live set when a consumer keeps every record.
- Producer fact: upstream `ElementsOptions` gains a node or memory budget (then the library inherits it and `maxElementNodes` is dropped before it ships).
- Risk: P2 for the number; P1 if no node budget exists and untrusted input is in scope (SPIKE-04's 122x case is a cheap denial of service).

## Architecture in one breath

effect-xml is a Schema codec whose encoded side is a resolved XML element: upstream `effect/encoding/Xml` tokenises and writes, a library Channel over its events resolves namespaces to expanded names and carries each element's prefix scope, an in-house per-record collector materialises one resolved element at a time under an inherited character limit and a node budget, and each consumer definition, written once in an object-form DSL, lowers to a closed `Plan` from which one compiler generates a single `Schema.decodeTo` per element into a Struct whose attribute and text leaves run through `Schema.toCodecStringTree`, whose child slots are the child codecs, whose `data-*` group is a template-literal `Record`, and whose mixed content is an ordered union indexed by each member's literal element name; decode and encode are the two directions of that one codec, round trip is canonical equivalence defined by an executable comparator, every failure names an XPath-like path translated from the struct-keyed Schema issue through the same `Plan`, and a line and column come from a post-hoc locate when the text is retained or an opt-in position channel when it is streamed.

## Phase-3 Schema JIT policy and fast-path fallback

Superseded in part by [Phase-3 policy revised (task `16f993dd`)](#phase-3-policy-revised-task-16f993dd): its F8 and F5 parts, and the F1 (a) trigger and F7.6 wording, no longer hold.

Ruling by `head-cto` on task `8aa826d9` (F1, F3, F5, F7.6, F8, F9), adopted by the Mind as written. Evidence: `docs/rd/perf3-spikes/jit.md` (`1d425f7`), `encode.md` (`3ec8e6d`), `builder.md` (`3ca760c`). This section is the recorded justification that `docs/goals/performance/phase-3.md` Non-goals require for any process-wide side effect. The wiring slices make it true; until they land, it describes the ruled design, not shipped code.

### F8 (a). Per-AST JIT on the library's own structural ASTs

**Ruling:** the library calls `SchemaJITCompiler.enable` on its structural decode AST, and on `SchemaAST.flip` of that AST for encode. It calls it once per AST, through one internal helper memoized in a `WeakSet`. It is on by default and adds no option. `SchemaJITCompiler` is `@stability unstable` in Effect 4.1.2, so it is imported in that one helper only (task `8aa826d9` F8).

Evidence (`jit.md` Q6, Q7):

- Per-AST equals the global import within noise: `base` on Bun 2.96 ms per-AST against 3.08 ms global, on Node 3.10 against 2.80 ms. Both compile the same 10 functions. Against the interpreter that is 1.89x on Bun and 2.55x on Node.
- Nothing is installed for unrelated schemas: an unrelated `Struct` generates 0 functions.
- There is no import-time effect. `enable(ast)` generates no code; generation happens on first decode or encode.
- Without eval, the JIT degrades to the interpreter at no cost: 1 failed probe, 0 compiled functions, an identical output fingerprint, and the interpreter's time (Bun 5.46 against 5.58 ms off; Node 7.81 against 7.91 ms). The encode path matches (`encode.md`: Bun 19.9 against 19.0 ms, Node 29.6 against 29.4 ms).
- `@computis/effect-xml` 0.4.0 does the same: `codec()` calls `enable` on its exact decoder AST and on the flipped AST unless `options.jit === false`.

Side effects, every one accepted (`jit.md` "Side effects", task `8aa826d9` F8):

1. **`compilerAdaptersEnabled`.** The first `enable` call flips this process-wide registry flag. Measured on a never-enabled interpreted codec, it changes nothing beyond noise (at most about 3%).
2. **Shared registry entries for user leaf ASTs.** Compiled entries live in Effect's global, AST-keyed registry and cover every AST reachable from the structural codec, including user leaf ASTs (`Schema.toCodecStringTree(userLeaf).ast === userLeaf.ast` for a `String`-typed leaf). After the library decodes or encodes, an application's own standalone decode of such a leaf runs the compiled entry. The JIT is trusted to preserve semantics, so this is a performance and eval-call side effect, not a behavioral one. Guard F7.7 (`perf3-diff-noeval`) checks it: the differential inputs run once by default and once with code generation blocked, and the fingerprints must match.
3. **Lazy `new Function` calls.** Code is generated on first use of each compiled AST, not at import or construction.
4. **Strict CSP or no-eval runtimes.** One `Function("return true")` support probe fails on the first compile attempt; then every node is interpreted. A browser with a CSP `report-uri` may also send one violation report for that probe; `jit.md` did not verify this.

Rejected options:

- **Global import** (`effect/schema/SchemaJITCompiler/enable`). It compiles every schema in the process, must run before first use, cannot be undone, and would make importing the library side-effectful (`jit.md` "Global import").
- **Documented opt-in, no library call.** Users could reach the JIT only through the global import, because the structural AST is not exposed, and everyone else forfeits 1.9x to 2.8x on the Schema step (`jit.md` "Documented opt-in").

Owner options, with their defaults (task `8aa826d9`, owner escalations):

- **`jit: false` opt-out.** A public API addition. Default: none in phase 3.
- **AOT install hook.** `SchemaAOTCompiler` reaches JIT speed without eval only when every composite node is a target, and the library builds its structural codecs at runtime from user declarations. AOT therefore needs a new public hook that exposes structural ASTs in a deterministic order, plus a user build step (`jit.md` Q7). Default: a later option, not phase 3.

### F1 (a) and F5. Fallback to today's path

- **Decode (F1 (a)).** The fast path answers only on success. On any builder refusal or structural decode failure, the library re-runs `Schema.decodeUnknownEffect(def)(element, parseOptions)` on the same collected root and returns exactly its outcome, including a success. Errors, paths, positions, `errors: "all"`, and `reason.cause` are therefore today's by construction (`builder.md` Recommendation 3; task `8aa826d9` F1, F2).
- **Encode (F5 (a)).** Text is written directly only when the current `Tokenizer` is `defaultTokenizer`, by identity; any other tokenizer receives the events through `tokenizer.encodeString()`. An illegal character, a non-string leaf, an unmapped attribute namespace, or a structural encode failure falls back to today's `encodeString` for the exact error (`encode.md` Recommendations 2 and 3; task `8aa826d9` F5).

### F3. Fast-path scope

The fast path lives only in `decodeString` (and so `fromString` decode), `decodeSchema`, `decodeSchemaString`, and `encodeString` (and so `fromString` encode). `compile()` output and every public AST stay as today. The structural codec is cached per `Plan` in a module `WeakMap` and is never reachable from a public AST. Direct Schema use of an element codec, including as a field of a user's Schema, keeps today's codec, today's speed, and identical derivations (task `8aa826d9` F3).

### F9. No excess-key check

The builder never emits a key the structural Struct does not declare: undeclared attributes and children are builder refusals under today's getter rules. The library sets no `onExcessProperty` and adds no `encodingChecks` filter. Caller parse options pass through unchanged, including `onExcessProperty` and `errors: "all"`; such a caller gets the same result but loses the compiled object loop (`jit.md` "Parse options matter"; task `8aa826d9` F9).

### F7.6. Leaves may run twice on failure

Under F1 (a) and F5, a user leaf transformation, or an effectful or service-using leaf, may run twice on a failed decode or encode: once in the fast attempt and once in today's path. This is not a stated contract (`Schema.Union` may already run a leaf more than once), so it is accepted (task `8aa826d9` F7.6; `encode.md` Recommendation 3 caveat). The JSDoc that the wiring slices touch states it as well.

### JIT: off by default (supersedes F8)

**Ruling:** the library enables no Schema JIT and no `src/` module imports `effect/schema/SchemaJITCompiler` or `effect/schema/SchemaJITCompiler/enable`. The structural codecs run interpreted. An application that wants the JIT imports `effect/schema/SchemaJITCompiler/enable` itself; the global compiler resolves every AST lazily, so it compiles the library's internal structural codecs too (`jit.md`, "unrelated Struct generated a function"), and the application owns that process-wide choice. `aa8309a` (`src/jit.ts`) was reverted by `ea23128`.

Why:

- **What the JIT is worth on the shipped path.** Measured end to end on the step-1 code (`df898ab`), with JIT on and JIT off in the same rounds under the owner's loaded-machine method (`performance.md`, "JIT on against JIT off, same rounds"; `docs/rd/performance/phase-3-ab/<runtime>-jit-on-vs-off-<input>.json`). The application's global import cuts CPU time per operation, on / off, median with a distribution-free interval of at least 95% coverage:

  | Case           | Input      | Bun                 | Node                |
  | -------------- | ---------- | ------------------- | ------------------- |
  | `typed-decode` | `bank-4m`  | 0.903 (0.879–0.915) | 0.835 (0.816–0.862) |
  | `typed-decode` | `bank-16k` | 0.906 (0.899–0.915) | 0.832 (0.825–0.852) |
  | `encode-typed` | `bank-4m`  | 0.847 (0.826–0.887) | 0.739 (0.704–0.761) |
  | `encode-typed` | `bank-16k` | 0.825 (0.813–0.844) | 0.772 (0.753–0.790) |

  That is about 10% (Bun) and 17% (Node) on decode and 15% to 26% on encode. The 3% and 6% decode figures this ruling first cited came from the `builder.md` spike's prototype, before the step-1 code existed. `errors: "all"` and `onExcessProperty` lose part of the gain (`jit.md`). The builder and writer win (about 8x and 5.6x) does not depend on the JIT. The section above leaned on `jit.md`'s hand-built codec (1.9x to 2.8x on the Schema step), which overstates the gain on the real structural codec.

- **What a per-AST enable costs.** `Registry.enable`'s scoped resolver writes a compiled entry for every reachable child that is not yet compiled, user leaf ASTs included, so the application's own later decodes of those leaves run order-dependently (`compilerRegistry.ts:222-235`; `SchemaJITCompiler.ts:83-84`). It flips the process-wide `compilerAdaptersEnabled` flag, puts an `@stability unstable` import on the default path, fires a support probe that a strict CSP refuses (a `report-uri` report is unverified), offers no opt-out, and adds a permanent differential axis. `phase-3.md` Goal 4 forbids an unjustified process-wide side effect, and a 10% to 17% decode and 15% to 26% encode CPU gain does not justify these in the library default.
- **Reversible.** Turning the JIT on later is additive; turning it off after shipping it on would be a regression release.
- **The measured gain does not change the ruling.** It is larger than the figure first cited, but it is not large, and an application already gets all of it by importing `effect/schema/SchemaJITCompiler/enable` itself: that import is the mode measured above. The default stays off. Whether the library adds a public `jit` opt-in remains an owner question.

Consequences: no-eval environments (Workers, strict CSP) get the same default as everyone; the bench `--jit off` mode keeps its meaning across the swap, so before and after rows compare like for like; guard F7.7 now compares the library default with the application's global import (`perf3-diff-noeval`). Owner option, non-blocking, and the default stands without an answer: a public `jit` opt-in, if Node encode parity with `@computis/effect-xml` matters (Node fast encode about 29.4 ms with the JIT off, against computis at about 14 ms, a figure derived from a `performance.md` ratio, not measured). The AOT hook stays a later option.

### Encode: always through the tokenizer (supersedes F5)

**Ruling:** encode always emits the writer's events into the current `Tokenizer`'s `encodeString()`, default or provided. There is no direct text writer and no `defaultTokenizer` identity check. With the JIT off, the direct writer and the events path are within noise: 19.0 against 21.0 ms on Bun, and 29.4 against 27.4 ms on Node, where events are faster (`encode.md`). The direct writer would duplicate upstream escaping, which can drift after an allowed `effect` bump, would skip upstream's name check for names the plan does not fix (`*` elements, opaque slots, `data-` keys), and would need an identity gate on an unexported value that any provided tokenizer or spread copy fails. Every encode now goes through the R9 seam, which keeps it exact. A direct writer is revisited only with the JIT on and a fresh measurement.

Today's `encodeString` runs for the exact error on a non-string leaf, any `spellAttributes` error (an unmapped attribute namespace among them), a non-element in an element position, a Schema failure of the structural encode, or an `XmlError` from `encodeString`.

### Fallback trigger and outcome rule (narrows F1 (a))

- The fallback runs after a builder or writer refusal, a Schema failure (`Fail`) of the structural decode or encode, or an `XmlError` from the tokenizer's `encodeString`, and its outcome, success or failure, is the result. A fast-path false reject followed by a fallback success always means a builder or structural gap, or a nondeterministic leaf; turning it into a defect would turn a performance bug into an outage.
- A defect or an interruption in the fast attempt propagates unchanged, with no rerun. Schema checks the encoded type before a getter runs, so a builder bug yields a `Fail`, not a throw, and a user leaf's defect is today's defect. Rerunning a throwing leaf would only double it, and rerunning after an interrupt is wrong.
- The fast attempt is `Schema.decodeUnknownEffect(structural)(plain, parseOptions)` (encode: `Schema.encodeEffect`) inside the caller's Effect, with the caller's services and environment; an async leaf suspends as it does today. Gating effectful leaves out of the fast path was rejected: `TransformEffect` is the only fallible getter and the service type is type-only, so a static gate would de-optimize every fallible leaf, Effect's own included.
- Surfacing: `xml.decodeString` and `xml.encodeString` carry `xml.codec` (`"structural"`, `"fallback"`, `"element"`) and, when it is `"fallback"`, `xml.fallback` (`"success"` or `"failure"`). The channel run span carries `xml.records.fallback` and `xml.records.fallback.accepted`.

### Double runs (replaces F7.6)

- Run counts: today's path is built lazily and runs only on a fallback (`5d5e049`). On a fast success, leaf code runs once. On a fallback, leaf code runs in the fast attempt, unless the builder refused before any user code, and once more on today's path, so the outcome returned is that second run's.
- Decode: a builder refusal runs no user code, because the builder is plain JavaScript over the collected record and runs before the structural decode. Leaf transformations run twice only when the structural decode ran and failed: once in the fast attempt and once in the fallback, whatever the fallback's outcome. This includes a fast attempt that fails and a fallback that then succeeds, which the section above did not say.
- Encode: only the open-`mixed` guard runs before the structural encode, so only its refusal runs no user code. The writer and the tokenizer run after the structural encode, so after a Schema failure of the structural encode, a writer refusal, or an `XmlError` from `encodeString()` (U+0000 among them, the commonest encode fallback), the leaf encodes that ran in the fast attempt run again in the fallback, whatever its outcome.
- The tokenizer's `encodeString()`, default or provided, can run twice on encode: once on the fast path's events, then again in today's encode after an `XmlError`.
- Recorded risk: a leaf whose outcome varies between runs can fail in the fast attempt and succeed in the fallback, and the fallback's outcome is returned. Double runs are not a stated contract (`Schema.Union` may already run a leaf more than once), so this is accepted.
- A mixed member's top-node checks run twice in today's codec (on the member, then on Schema.toType of it inside the item) and once on the faster path. A check whose verdict and side effects do not vary gives the same outcome. A check with side effects observes one call where today it observes two, and three after a fallback (ruled on head-cto task `ae30d930`, residual R5).

### Same value

Two decoded values are the same when Vitest `toStrictEqual` holds (deep equality, prototype or class, own-property presence, array sparseness) and every object's own-key order is equal at every depth. Reference identity is not part of the contract. Encode sameness is byte-identical text, and events equal by `JSON.stringify`. The builder emits keys in today's order: attributes in element order, then content keys.

### Checks carry-over and spelling (amends F4 (a))

- Checks on a compiled element's top node, including `Schema.fromBrand` (`.check(...ctor.checks)` then `brand`, `node_modules/effect/src/Schema.ts:5343-5352`), are carried onto the structural node with the same `Filter` objects, so a checked root or slot keeps the fast path; a value the check rejects falls back for the exact error. `decodeTo` and every transformation stay opaque. `jit.md` measured checks at no fast-path cost (struct-check 2.93 against base 2.96 ms). The carry-over lands as a follow-up slice, `perf3-checked-wrappers`; `perf3-slot-predicate` ships strict first. The carry-over is not prototyped; that slice proves it.
- Spelling dependence, recorded: the fast path depends on how the caller spells the decode, because public ASTs stay unchanged (F3). `fromString(def)` and the channels get it; `ElementFromString(...).pipe(Schema.decodeTo(Root))`, a direct `Schema.decode` of an element codec, and an element codec inside a user's `Struct` run today's codec at today's speed. The consumer JSDoc of the fast entry points says so in plain words. A `SchemaCompiler.set` decoder for `compile()` ASTs (`node_modules/effect/src/SchemaCompiler.ts:216`, `@stability unstable`) is a later option, unverified.

### Carried checks

perf3-checked-wrappers (813755c) moves a structural element's top-node checks onto its structural codec. These are the checks written with Schema.check and the ones Schema.fromBrand adds, and the move keeps the same Filter objects. A filter receives three arguments: the Type value, the AST node being parsed, and the parse options. The Type value and the parse options are the ones today's codec passes. The node is not: on the faster path it is the structural codec's internal node, which carries no element marker. A filter whose verdict depends only on the value and the options decides the same on both paths; every Effect built-in check and every Brand.check constructor is such a filter. A filter whose verdict reads the node can pass on the faster path where today's codec rejects, and that pass is returned with no fallback. This is accepted for two reasons. Effect itself runs the same filter against different nodes: a Brand.check constructor runs a fromBrand filter with the unknown keyword as the node (SchemaAST.runChecks), so the node is not part of a filter's contract. And no test can tell a node-reading filter from any other, because Filter.run is an opaque closure. Ruled on head-cto task ae30d930 (audit 7aa62827, residual R1).

## Phase-3 resolution: fromString passes the decoded value through

The owner chose option B (`work/owner-directive-perf3-continue.md`, item 1) over A (reject overlapping members at definition time) and C (record and change nothing). Diagnosis: head-cto task `53621056`.

- `fromString(def)` decodes text with `decodeString(def)` into a passthrough declaration over `Schema.toType(def)` (`passedValue` in `src/document.ts`). The declaration's parser returns its input, so the decoded value is not re-parsed on the type side. Its equivalence, formatter, iso, and arbitrary derivations delegate to `Schema.toType(def)`.
- A `fromString` decode equals `decodeString(def)`, including on a type-side union whose earlier member accepts a later member's value: overlapping mixed members and text or attribute leaf unions told apart only on the encoded side (`src/document.test.ts`).
- Encode validates through `encodeString(def)`: a value `def` rejects fails there.
- The root's checks run once per decode and once per encode.
- `Schema.is`, `Schema.asserts`, and `Schema.toType` of a `fromString` codec do not check the value's shape; they fail open. The `fromString` doc comment says so and names the safe check, `Schema.is(Schema.toType(def))` or `Schema.asserts(Schema.toType(def))` on the element codec. `src/document.test.ts` pins both directions. The owner chose to keep fail-open (2026-11-07, mail `17ecc486`).
- Two deltas against the frozen oracle were accepted; the resulting `fromString` shape (`Encoding<Declaration>` outer tree on a failed decode; `XmlEncodeError` with `EncodeSchemaFailure` on a rejected encode) is pinned in `test/differential/harness.test.ts` since the oracle's deletion in `e35151d`. ### Encode resolution: one member per collision group

The owner directive's item 1 also asked that encode write the right member when mixed members share a wire tag. Ruled in head-cto `e4e2f621` (B2, B3, B4), with the Mind taking the `oneOf` default.

- A collision group is the set of members of one `mixed` content that share a wire tag or a Clark name (`collidingMembers` in `src/plan.ts`). `src/compile.ts` and `src/structural-slot.ts` both read it, so the compiled rule and the opaque rule cannot disagree.
- Content with a group compiles its items union with `mode: "oneOf"`, and each group member's item holds its value through an exact declaration (`exactValue` in `src/compile.ts`): it parses the member's type side with `onExcessProperty: "error"`. Encode writes the one member that accepts the value with no excess key: `{ y: "1" }` against `p` in `urn:a` with `x?` and `p` in `urn:b` with `y` writes `<p xmlns="urn:b" y="1">`, where the oracle wrote `<p xmlns="urn:a">` and lost `y`.
- New failures, inside a group only: a value no member accepts exactly fails (an excess key is not dropped); a value two members accept exactly fails with the exactly-one error; a document two Clark-duplicate members both decode fails the same way. `src/issue.ts` names the group members that matched (wire, namespace, author position), read from each item's position in the compiled union, so the names hold with three or more members and with `suspend` members, which the union tries last. The library message is used in both directions; the repair sentence differs by direction. The repair names the cause the members report: an excess key, a missing key, or a value of the wrong type.
- Round-trip caveat: decode picks a member of a wire-tag group by its Clark name, not by its exact shape, so a decoded value can fail to encode. With `p` in `urn:a` with `x?` and `p` in `urn:b` with `z?`, `<r><p xmlns="urn:b"/></r>` decodes to `{ _tag: "p", value: {} }`, and encoding that value fails with the exactly-one error, where the oracle wrote `urn:a`. The advice, also in the README, is to make the members of a group distinguishable by required keys.
- The JSON Schema of a group-bearing root's type side (`Schema.toType(root)`) gives its `$children` items as `oneOf` instead of `anyOf`, a direct consequence of the `oneOf` union. The encoded side's JSON Schema and every group-free root are unchanged.
- Content without a group compiles to the same AST as before: the default union and each member's own type side (`src/compile.test.ts`). F9 still holds for the fast path, which never sees a group; `onExcessProperty` is set only inside a group member's declaration on the compiled codec.
- The dae32dd workaround stays (B3): an element with a group stays on the compiled codec, since the builder, the structural codec, and the writer select a member by Clark name or wire tag alone.
- Named expectation changes in `test/mixed-ambiguity.test.ts`: the encode rows `wire` (y present), `clark`, and `holder` carried their `encoded` text and asserted the oracle wrote a different one (those contrast assertions were removed in `212e711`, which pinned the rows to literal `src` outcomes before the oracle's deletion in `e35151d`; the rows now pin literal expectations, and this record keeps the before and after), and the src-only rows pin the three failures, the members named with three Clark duplicates and with a `suspend` member, the cause-specific repair, and the unchanged stripping outside a group. No other differential suite changed.
